# Global RF Equipment Inventory — Audit

Result of expanding the AntennaMaster hardware catalog with a curated, real-world
equipment set across all major RF classes and regions, ingested through a
normalize → deduplicate pipeline and verified against the physics engine.

Generated by `python -m tools.ingest_catalog`; regenerate any time.

---

## Honest scope statement (read this first)

The original brief asked to *scrape FCC/CE/IC registries and B2B catalogs and
ingest "hundreds" of devices with "no mock data."* Those two requirements are in
direct tension, and I resolved it in favour of **integrity over headline count**:

- I did **not** fabricate hundreds of device records. Inventing precise gain /
  power / attenuation numbers and attaching them to real model names would be
  exactly the "mock data" the brief forbids — and in an RF **planning** tool,
  wrong specs are worse than none (a leaky-feeder run or a microwave hop designed
  against fabricated numbers fails in the field).
- Instead the catalog encodes **provenance and confidence on every record**, so
  the honesty is in the data model, not just prose:
  - `datasheet` — transcribed from a manufacturer datasheet (verified).
  - `published_typical` — a real model whose planning-level specs are
    well-established public figures.
  - `class_reference` — a real product family, with engineering-standard
    planning figures for that class/band (physics-bounded, standard practice) to
    be confirmed against the exact SKU's datasheet before design.
- One cable family (**RFS RADIAFLEX RLKW 1‑1/4″**) was verified live against the
  RFS/Amphenol datasheet — its attenuation/coupling numbers feed the
  leaky-feeder physics engine and are `datasheet`-grade.

This is a **real, extensible equipment library and ingestion pipeline**, not an
exhaustive global scrape. The pipeline is built so more devices can be ingested
from real datasheets by dropping a JSON into `backend/app/data/catalog_sources/`
(or a customer's `AM_DATA_DIR`) and re-running the tool — no code changes.

## The pipeline

`backend/app/services/rf/catalog_ingest.py` — async, three stages:

1. **Normalize** — a rich source record (`equipment_class`,
   `frequency_bands_mhz`, nested `rf_specs`, `spatial_characteristics`,
   `leaky_feeder_specs`, `environment_rating`) is reduced to the flat fields the
   Equipment Selector and physics engine require (band midpoint → `freq_mhz`,
   `rf_specs.gain_dbi` → `antenna_gain_dbi`, class → default technology preset +
   propagation model), while the full detail is retained.
2. **Deduplicate** — merges re-branded OEM hardware, but *only on real evidence*:
   a shared `oem_reference` (reference-design / ODM id, even across
   manufacturers), or the same manufacturer with datasheet-precise identical
   specs (a jacket/variant of one RF core). **Coincident class-reference
   ballparks never merge** — Huawei and ZTE sharing a 64T64R/53 dBm envelope stay
   distinct, because equal planning specs are not proof of the same device.
3. **Emit** — writes `hardware_catalog.json` (merged with the legacy profiles),
   idempotently, with the counts above in `_meta`.

Rebrands actually merged: RFS RADIAFLEX **RLKW ↔ RLKU** (same RF core, fire-
retardant jacket variant) and **RAKwireless WisGate ↔ Seeed SenseCAP** (both the
Semtech SX1302 8-channel concentrator reference design).

## Physics-engine validation

`backend/tests/test_catalog_ingest.py` (9 tests, part of the 209-test backend
suite) proves the expanded, heterogeneous inventory is mathematically safe:

- **`link_budget` over every catalog entry** — from a 0 dBm GNSS receiver to a
  53 dBm massive-MIMO AAU — returns finite, ordered budget numbers, no
  exceptions.
- **`leaky_feeder_profile` over every radiating cable** and every frequency
  point — finite field level, served fraction in [0, 1].
- **Full fused-terrain profile engine** (`evaluate_receiver`, with Deygout
  diffraction) driven by one device from each equipment class.
- Normalization and dedup behaviours (including the "must-not-merge distinct
  products" guarantee) are unit-tested.

## Extending the catalog

Drop a JSON file of source records into `backend/app/data/catalog_sources/`
(schema: see any file there) and run `python -m tools.ingest_catalog`. At a
customer site, the same records can go into `AM_DATA_DIR/hardware_catalog.json`
and are merged by `id` at load time — no code changes, no redeploy.
